# Offset-пагинация

`createInfiniteQuery` устроен вокруг курсора: вы отдаёте ему `pageParam`, он возвращает
следующий. **Офсет** — это курсор, который по совместительству является позицией в серверном
списке, а позиции двигаются. Как только элементы вставляют, удаляют или переупорядочивают,
офсеты ещё не загруженных страниц указывают уже не туда, куда указывали секунду назад.

Движение бывает двух сортов, и чинятся они по-разному:

- **Подвинул сервер** — кто-то опубликовал запись, элемент удалили. Локально пропуск или
  дубликат не предотвратить: дедуплицируйте при добавлении и перезагружайте, когда это важно.
- **Подвинули вы** — оптимистичная вставка, элемент, поднявшийся наверх после обновления,
  локальное удаление. Вот это уже ваша ответственность — и именно это тихо портит ленту.

## Выберите курсор, который не уезжает

Соблазнительный `getNextPageParam` считает уже загруженное:

```ts
// ✗ уезжает: после локальной вставки лента считает, что получила от сервера на элемент больше
getNextPageParam: ({ allPages }) => {
  const loaded = allPages.flatMap((p) => p.items).length;
  return loaded < total ? loaded : null;
};
```

Выводите его из параметров страниц — они фиксируют то, что вы реально **запрашивали**, и
локальные правки на это не влияют:

```ts
// ✓ устойчиво: следующий офсет считается от последнего запрошенного
getNextPageParam: ({ lastPageParam }) => (lastPageParam + SIZE < total ? lastPageParam + SIZE : null);
```

Разница на ленте из страниц по 2 элемента после одной оптимистичной вставки наверх:

| курсор                       | следующий запрос | результат                   |
| ---------------------------- | ---------------- | --------------------------- |
| `allPages.flatMap(…).length` | офсет **5**      | `i5, i6` — **`i4` потерян** |
| `lastPageParam + SIZE`       | офсет **4**      | `i4, i5` — верно            |

Подсчёт безопасен ровно до тех пор, пока в `$pages` лежит в точности то, что вернул сервер, —
а это перестаёт быть правдой при первой же локальной правке.

## Дедупликация при добавлении

Даже с устойчивым курсором можно получить уже показанный элемент: между двумя запросами сервер
сдвинулся. Добавленная страница попадает в `$pages` как есть, поэтому дедуплицируйте там, где
читаете ленту, — по id:

```ts
const $items = feed.$pages.map((pages) => {
  const seen = new Set<string>();
  return pages
    .flatMap((p) => p.items)
    .filter((item) => (seen.has(item.id) ? false : (seen.add(item.id), true)));
});
```

Если держать дедупликацию в производном сторе (а не мутировать `$pages`), тела страниц
продолжают соответствовать своим `pageParams`, и `refetchAll` остаётся рабочим.

## После локальной вставки или удаления

Локальная правка сдвигает все последующие офсеты на единицу. Вариантов три, по возрастанию
цены:

**Смириться со сдвигом и перезагрузить.** Самое простое корректное решение: дать оптимистичной
вставке отрисоваться, а при следующем обновлении списка вызвать `feed.start(params)`. Один
лишний запрос и никакой бухгалтерии.

**Нести сдвиг в курсоре.** Держите счётчик локальных вставок минус удалений и применяйте его
там, где считается следующий офсет:

```ts
const $localShift = createStore(0)
  .on(todoInserted, (n) => n + 1)
  .on(todoDeleted, (n) => n - 1)
  .reset(feed.start);
```

Читайте его там, где строится офсет (через `source` у эффекта страницы или в своей обёртке над
`fetchNext`): `getNextPageParam` — чистый колбэк и сторы читать не должен.

**Патчить страницы, сохраняя честные параметры.** `update` / `optimisticUpdate` пишут через
`__.setData`, который пере-выводит курсоры из пропатченных страниц:

```ts
update({
  query: feed,
  on: addTodo,
  fn: ({ data, result }) => [{ items: [result, ...data[0].items] }, ...data.slice(1)],
});
```

Обратите внимание, что при этом происходит с `$pageParams`: они **обрезаются до нового
количества страниц**. Пропатчите окно из трёх страниц (`pageParams: [0, 2, 4]`) до одной — и
параметры станут `[0]`, так что последующий `refetchAll` перезагрузит одну страницу, а не три.
Либо сохраняйте количество страниц при патче, либо будьте готовы, что окно схлопнется вместе с
ним.

## `refetchAll` против `start` на переупорядоченном окне

`refetchAll` перезапрашивает **сохранённые** `pageParams` и заменяет окно тем, что пришло. Для
локально переупорядоченной ленты это означает, что локального порядка больше нет:

```
локальное окно:    MOVED, i0, i1, i2, i3
refetchAll просит: офсет 0, офсет 2
окно после:        i0, i1, i2, i3          ← MOVED пропал, вернулся серверный порядок
```

Это верное поведение, когда вам нужна правда с сервера, и неверное, когда пользователь всё ещё
смотрит на собственную оптимистичную правку. Выбирайте так:

- **`refetchAll`** — фоновое обновление окна, которое пользователь не правил (поллинг,
  инвалидация по тегу, реконнект).
- **`start`** — после локальной правки и после всего, что обесценивает старые офсеты (смена
  фильтра, смена сортировки). Он сбрасывает окно и грузит первую страницу, так что ничего
  устаревшего не остаётся.

## Когда просить у бэкенда курсор

Офсеты — это обходной путь для списка, который меняется. Если лента живая — соцлента, список
уведомлений, что угодно со вставками наверх, — ничто из перечисленного не лечит её полностью:
два пользователя всегда могут вклиниться записью между вашими запросами страниц. Keyset-/
курсорное API (`?after=<id>`) делает границу страницы _значением_, а не _позицией_, поэтому
последующие страницы остаются корректными независимо от того, что произошло до них.

Просить стоит, когда видите: дубликаты на стыках страниц при обычной работе, пропавшие
элементы, которые пользователь точно видел, или `getNextPageParam`, обрастающий поправочными
коэффициентами. С курсором всё описанное выше схлопывается в:

```ts
getNextPageParam: ({ lastPage }) => lastPage.nextCursor ?? null;
```
